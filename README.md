# Красуня — MVP запису салону

Локальний інтерактивний прототип українською мовою з демо-даними.

## Запуск демо без backend

```bash
python3 -m http.server 4173
```

Після цього відкрити [http://localhost:4173](http://localhost:4173).

## Запуск із постійним зберіганням даних локально

```bash
python3 server.py
```

Після цього відкрити [http://localhost:4173](http://localhost:4173). Backend створить поруч файл `krasunya.sqlite3`, заповнить його демо-даними та обслуговуватиме frontend і API.

Можна вказати інший порт або файл бази:

```bash
PORT=4174 KRASUNYA_DB=/private/tmp/krasunya.sqlite3 python3 server.py
```

## Запуск на Vercel із постійним зберіганням

На Vercel SQLite-файл у `/tmp` є тимчасовим, тому production-режим використовує PostgreSQL. Після підключення Neon до проєкту Vercel додайте автоматично створену змінну `POSTGRES_URL` або `DATABASE_URL` для середовищ Production і Preview. Файл `requirements.txt` додає драйвер PostgreSQL, а `api/index.py` автоматично створює таблиці та демо-дані під час першого запуску.

Перевірити тип сховища можна через `GET /api/health`: відповідь містить `storage: "postgres"` для production-бази або `storage: "sqlite"` у локальному fallback-режимі.

Основні API-маршрути:

- `GET /api/health` — перевірка сервера.
- `GET /api/auth/session` — поточний сеанс.
- `POST /api/auth/login` і `POST /api/auth/logout` — вхід та вихід.
- `POST /api/auth/password` — зміна власного пароля адміністратора, майстра або клієнта.
- `POST /api/auth/branch` — зміна філії адміністратором або клієнтом.
- `GET /api/bootstrap` — дані для frontend.
- `POST /api/branches`, `POST /api/branches/:id/close` і `DELETE /api/branches/:id` — створення, закриття та видалення філії адміністратором. Закриття позначає філію закритою, переносить записи, кабінети, обладнання та неробочий час в архів і блокує нові операції; адміністратор може переглядати архів. Закриту філію видалити не можна.
- `POST /api/admins` і `DELETE /api/admins/:id` — додавання та видалення інших адміністраторів.
- `POST/PATCH/DELETE /api/masters`, `/api/rooms`, `/api/equipment`, `/api/procedures` — керування довідниками адміністратором.
- `POST /api/bookings` — створення запису із серверною перевіркою ресурсів.
- `PATCH /api/bookings/:id` — перенесення запису з повторною перевіркою або скасування через `{"status":"cancelled"}`; скасований запис зберігається в історії, але звільняє ресурси.
- `POST /api/availability` — додавання неробочого часу.
- `PATCH /api/availability/:id` і `DELETE /api/availability/:id` — зміна та видалення інтервалу.

Перевірка backend:

```bash
python3 -m unittest -v test_server.py
```

## Що перевірити

- Вхід як «Адміністратор», «Майстер» або «Клієнт» із розмежуванням доступів.
- Перемикання філій адміністратором і клієнтом; створення нової філії доступне адміністратору.
- Відкриття налаштувань профілю та вихід із системи через обліковий запис у нижній частині меню.
- День/тиждень/місяць/рік у розкладі: при відкритті обирається поточна дата, а стрілки, календар і кнопка «Сьогодні» перемикають періоди без синхронізації із зовнішнім календарем.
- Створення нового запису через «Новий запис».
- Вибір процедури для додавання, таймлайн доступності з етапами, майстрами, кабінетами й обладнанням, список процедур у візиті та рекомендація майстра за історією клієнта.
- Додавання неробочого часу майстра з ролі адміністратора або майстра та перевірка, що новий запис не потрапляє в цей інтервал.
- Перевірка послідовного маршруту Glow Reset.
- Конфлікт ресурсів при виборі зайнятого часу.
- Перенесення запису адміністратором або майстром через картку візиту; усі етапи зсуваються разом і повторно проходять перевірку конфліктів.
- У розділі «Клієнти» адміністратор бачить усіх, а майстер — лише клієнтів зі своїми попередніми або новими записами.
- Фото майстрів у записах, команді та особистому кабінеті клієнта. Фото можна завантажити з пристрою прямо у формі майстра; браузер автоматично зменшує його перед збереженням.
- Закриття філії через перемикач локацій: активні операційні дані архівуються, працівники та клієнти втрачають доступ до закритої філії, а адміністратор бачить її статус і підсумок архіву.
- Довідники процедур, кабінетів, обладнання, команди, клієнтів та історії. Команда, кабінети, обладнання й процедури ізольовані за філіями; адміністратор може додавати, редагувати й видаляти їх у поточній філії, а видалення ресурсу, який використовується в записах або маршрутах, блокується сервером.
- Зміна пароля в налаштуваннях профілю для кожної ролі з перевіркою поточного пароля та підтвердженням нового.

У демо-режимі стан зберігається в пам’яті браузера й скидається після перезавантаження. При запуску через `server.py` записи та неробочий час зберігаються в SQLite, а остаточна перевірка конфліктів виконується на сервері в транзакції.
